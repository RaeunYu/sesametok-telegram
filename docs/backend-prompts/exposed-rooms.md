# 백엔드 작업 지시서 — 노출 대상 방(exposed rooms)

> 이 문서는 **다른 저장소(`sesametok-telegram`, 텔레그램 클라이언트)의 설계 인터뷰 결론**을
> 이 저장소(`sesametok-backend`) 에이전트에게 넘기는 작업 지시서입니다.
> 이 문서에 적힌 것만 하세요. 여기 없는 개선·리팩터링·기능 추가는 하지 마세요.

---

## 1. 배경과 목적

- 텔레그램 클라이언트가 이 백엔드에 붙습니다. 아카이브는 지금처럼 **전체 방(현재 411개 내외)을
  동기화**합니다. 바뀌는 것은 "그중 **어떤 방을 외부 채널에 노출할지**"입니다.
- 노출 대상은 **사용자가 직접 지정**합니다. 기본값은 **아무 방도 노출되지 않음**입니다.
- 이 선택 정책을 **클라이언트마다 중복 구현하지 않습니다.** 저장·UI·API 표면을 백엔드가 단일
  출처로 소유합니다.
- 사용자가 노출 방을 바꿀 수 있는 표면은 **두 개**여야 합니다.
  1. 메뉴바 드롭다운(맥 앞에 있을 때)
  2. HTTP API(클라이언트·모바일에서 원격으로)

  **메뉴바 전용이면 안 됩니다.** 이 프로젝트의 존재 이유가 "맥 앞에 없을 때도 카톡을 쓰는 것"인데,
  노출 방 변경이 메뉴바에만 있으면 그 목적과 모순됩니다.

---

## 2. 확정 사항 (설계 결정 — 재론하지 말고 그대로 구현)

1. **저장 위치**: 아카이브의 `rooms` 테이블에 `exposed INTEGER NOT NULL DEFAULT 0` 컬럼을
   추가합니다. 기존 `is_from_me` 마이그레이션과 **같은 방식**(`core/archive.py`의 마이그레이션
   목록 + 시작 시 정합화 패턴)을 따르세요. 마이그레이션 이후 새로 발견되는 방의 기본값은 `0`.
2. **노출은 메타데이터다.** `Room` 모델에 `exposed: bool`을 추가하고 **모든 Room 응답에 포함**
   합니다(`/v1/rooms`, `/v1/rooms/{chat_id}`, `room.updated` 이벤트 payload).
3. **`GET /v1/rooms`의 기본 동작은 바꾸지 않습니다.** 쿼리 `exposed=1`(또는 `exposed=true`)이
   있으면 노출된 방만 반환합니다. 생략 시 지금과 동일하게 전체 반환. 그 밖의 값은 `400 bad_request`.
4. **쓰기 경로**: `PATCH /v1/rooms/{chat_id}` with body `{"exposed": true|false}` → `200` + Room
   객체(변경 반영). 멱등이어야 합니다. 없는 `chat_id` → `404 room_not_found`,
   `exposed`가 JSON boolean이 아니거나 본문이 객체가 아님 → `400 bad_request`.
5. **`PATCH` 성공 시 `room.updated` 이벤트를 발행**합니다(payload는 Room 전체). 메뉴바에서
   토글한 사실을 클라이언트가 즉시 알 수 있어야 하기 때문입니다. 이벤트 `seq`를 소비합니다.
6. **이벤트 스트림(SSE·webhook)은 절대 필터링하지 않습니다.** 이유: `CLIENT_INTEGRATION.md`
   5.2절의 **갭 감지가 `seq` 연속성에 의존**합니다. 서버가 비노출 방 이벤트를 빼면 정상적인
   `seq` 점프가 생기고, 클라이언트는 그것을 유실로 오판해 불필요한 REST 보정을 돌립니다.
   거르는 일은 노출 집합을 이미 들고 있는 클라이언트가 합니다.
7. **발신은 노출 여부와 무관하게 동작합니다.** 노출은 "보여줄 방"이지 "보낼 수 있는 방"이
   아닙니다. `POST /v1/messages`에 노출 게이트를 추가하지 마세요.
8. **벌크 엔드포인트를 만들지 마세요.** 다건 설정은 클라이언트가 단건 `PATCH`를 반복합니다.
   방이 수백 개라도 실제로 지정하는 방은 소수입니다.

## 3. API 계약 상세

### `Room` (응답 필드 추가)

기존 필드 이름·타입·순서를 바꾸지 말고 `exposed`만 추가합니다.

```json
{"chat_id": "…", "chat_name": "…", "chat_type": "direct",
 "last_message_at": "2026-10-19T06:46:02+00:00", "message_count": 3, "exposed": false}
```

### `GET /v1/rooms?exposed=1`

```json
{"rooms": [ … exposed 가 true 인 방만 … ]}
```

- `exposed` 생략 → 전체(기존과 동일).
- `exposed=1` / `exposed=true` → 노출된 방만.
- 그 밖 → `400` + `{"error":{"code":"bad_request",…}}`.
- 정렬은 기존 규칙(`chat_id` 오름차순) 그대로.

### `PATCH /v1/rooms/{chat_id}`

요청:

```json
{"exposed": true}
```

응답 `200`: Room 객체 하나(변경 반영). 오류: `400 bad_request` / `404 room_not_found` /
`401 unauthorized` / `405 method_not_allowed`(다른 메서드).

- 같은 값으로 다시 호출해도 성공(멱등).
- 이 호출은 카카오톡을 건드리지 않습니다. 아카이브 메타데이터만 바꿉니다.

## 4. 메뉴바 UI

- 드롭다운 최상위 영역에 **`노출 방 관리…`** 항목을 추가하고, 라벨에 현재 상태를 요약합니다
  (예: `노출 방 관리… (7/411)`).
- 창을 열면:
  - **검색 입력** (방 이름 부분 일치). 411개를 스크롤로만 훑게 만들면 쓰지 못합니다.
  - **체크박스 목록**, 최근 메시지 시각 내림차순. 각 행에 방 이름 + `chat_type` 정도만.
  - **`저장` / `닫기`**. 저장 시 바뀐 방만 `PATCH`와 **같은 내부 함수**로 반영합니다
    (API·메뉴바가 같은 경로를 타야 합니다. 로직을 두 벌 만들지 마세요).
- AppKit 규칙(메인 스레드 전용)을 지키고, 기존 메뉴바 코드의 패턴을 따르세요.
- **방 이름을 로그에 남기지 마세요**(`AGENTS.md` 규칙). 개수와 id만.

## 5. 테스트 (반드시 추가)

1. `PATCH` 성공 → `200`, 응답 `exposed` 반영, 두 번째 호출도 `200`(멱등).
2. `PATCH` 없는 `chat_id` → `404 room_not_found`.
3. `PATCH` body가 `{"exposed": "true"}`(문자열) 또는 객체 아님 → `400 bad_request`.
4. `GET /v1/rooms?exposed=1` → 노출된 방만. 생략 시 전체. `exposed=2` → `400`.
5. Room 직렬화에 `exposed` 포함, **기존 필드 불변**.
6. 마이그레이션: `exposed` 컬럼이 없는 아카이브를 열면 컬럼이 생기고 기존 행이 `0`으로 채워짐.
7. `PATCH`가 `room.updated` 이벤트를 발행하고 `seq`를 소비함.
8. **회귀 방지 — 스트림은 필터되지 않는다**: 비노출 방의 `message.created`도 SSE에 그대로 나온다.
9. 메뉴바 선택 로직은 **UI 없이 테스트 가능한 순수 함수**로 분리해 단위 테스트(검색 필터,
   변경분 계산, 저장 호출).
10. 기존 테스트 전부 green.

## 6. 문서 갱신

- `CLIENT_INTEGRATION.md`
  - 3절 Room 표에 `exposed` 행 추가(의미: "외부 클라이언트에 노출하기로 사용자가 지정한 방").
  - 4.2절 `/v1/rooms` 쿼리 설명 + `PATCH /v1/rooms/{chat_id}` 절 신설.
  - 7절 "하면 안 되는 것"에 **"노출 목록을 클라이언트마다 따로 관리"** 항목 추가(대신: API로 읽고 쓸 것).
  - **"이벤트 스트림은 노출 여부로 필터되지 않는다 — 클라이언트가 거른다"** 를 명시.
  - `PATCH`가 `room.updated`를 만든다는 사실 명시.
  - 6.3절 실측 테스트 수 갱신.
- `DECISIONS.md`
  - **ADR-023: 노출 대상 방 정책은 백엔드가 소유하고, 이벤트 스트림은 필터하지 않는다.**
    근거에 다음을 포함: (a) 다중 클라이언트의 단일 출처, (b) 인간용 표면이 이미 메뉴바에 있음,
    (c) **메뉴바 전용이면 "맥 앞에 없을 때도 쓴다"는 제품 목적과 모순되므로 API 쓰기 경로를
    함께 연다**, (d) **서버 측 이벤트 필터링은 `seq` 연속성 기반 갭 감지 계약을 깨므로 금지**,
    (e) 노출은 허용이 아니므로 발신 게이트가 아니다.

## 7. 하지 말 것

| 금지 | 이유 |
|---|---|
| `/v1/rooms` 기본 응답을 "노출만"으로 바꾸기 | 기존·미래 클라이언트의 계약 파괴 |
| SSE·webhook 이벤트 필터링 | `seq` 연속성 기반 갭 감지가 깨진다 |
| 발신에 노출 게이트 추가 | 노출은 표시 범위이지 발신 허가가 아니다 |
| 메뉴바 전용 UI로 끝내기 | 원격에서 노출 방을 바꿀 수 없으면 제품 목적과 모순 |
| 벌크 토글 엔드포인트 | 단건 `PATCH` 반복으로 충분. 계약만 늘어난다 |
| 구독·알림·음소거 같은 클라이언트 UX 개념 도입 | 이 저장소는 어댑터가 아니다 |
| 텔레그램·Slack 관련 코드나 의존성 | 이 저장소는 외부 네트워크로 나가지 않는다 |
| 방 이름·메시지 본문을 로그/문서에 남기기 | 개인정보 |
| 기존 응답 필드의 이름·타입 변경 | 추가형 변경만 허용 |
